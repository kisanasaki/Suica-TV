# コードコメント規約

## 目的

コメントはコードの日本語訳ではなく、責務、契約、判断理由、不変条件、失敗時の挙動を将来の変更者へ伝えるために使用する。

## 共通ルール

- すべての手書きコードへファイルヘッダーを置き、目的、主な責務、責任境界を3〜12行程度で記載する。
- 本文では公開API、状態遷移、排他制御、セキュリティ、OS依存処理、意図的なフォールバックを優先して説明する。
- 識別子、API名、Wire上の値、一般的な技術用語は英語表記を保ち、それ以外は日本語で記載する。
- 作者、作成日、更新日、変更履歴はGitと重複するため記載しない。
- 代入や分岐をそのまま言い換えるコメント、テスト名を繰り返すコメントは追加しない。
- 未確認の挙動を保証として記載しない。配送成功と実処理成功など、保証範囲が異なる場合は境界を明記する。
- TODOを追加する場合は追跡先を持つ`TODO(#issue): 理由`形式にする。

## 言語別形式

- Rust: ファイルヘッダーは`//!`、公開契約は`///`、実装理由は`//`。
- TypeScript/TSX: ファイルヘッダーとexportされた主要APIは`/** ... */`、実装理由は`//`。
- Swift: ファイルヘッダーは`//`、主要な型とメソッドはDocCの`///`。
- Shell: shebang直後に`#`で目的、入出力、安全性を記載する。
- CSS: ファイル先頭に`/* ... */`を置き、テーマ、レイアウト、状態、レスポンシブのまとまりだけを区切る。

## テストコード

- ヘッダーには対象機能と守るべき回帰条件を記載する。
- 長い結合試験では、接続確立、障害注入、復旧確認など意味のある段階だけをコメントする。
- Arrange / Act / Assertを機械的に付けない。

## 対象外

自動生成された宣言ファイル、Xcodeプロジェクト、lockfile、ビルド生成物には手動コメントを追加しない。
